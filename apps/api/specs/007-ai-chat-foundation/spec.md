## User Scenarios & Testing *(mandatory)*

### User Story 1 - 비회원 질문 제출 (Priority: P1)

방문자는 가입이나 로그인 없이 현재 질문과 필요한 최근 대화를 하나의 요청으로 제출한다. AI 안내·검색은 브랜드와 작업물을 이해하기 위한 기능이며 실제 제작 상담은 카카오톡 채널의 책임이다.

**Why this priority**: 방문자 식별이나 상담 기록 복원 없이 사용할 수 있는 공개 진입점이 필요하다.

**Independent Test**: 인증 정보가 없는 요청과 제어 가능한 이벤트 소스로 질문 수락 여부를 검증한다. 실제 AI 답변 생성은 검증 대상이 아니다.

**Acceptance Scenarios**:

1. **Given** 유효한 질문과 최근 대화, **When** 공개 POST API 호출, **Then** 검증된 입력이 스트리밍 처리 경계로 전달된다.
2. **Given** Admin Session과 방문자 식별 쿠키가 없는 요청, **When** 유효한 질문 제출, **Then** 가입·로그인·장기 식별자를 요구하지 않는다.
3. **Given** 이전 대화가 없는 첫 질문, **When** 빈 `history` 또는 `history` 생략, **Then** 현재 질문만으로 수락한다.
4. **Given** 유효하지 않은 JSON 또는 필수 값 누락, **When** 요청 제출, **Then** SSE 시작 없이 일반 HTTP 오류를 반환한다.

### User Story 2 - 점진적인 답변 수신 (Priority: P1)

클라이언트는 같은 POST 응답에서 시작, 여러 텍스트 조각, 정상 완료를 순서대로 구별한다.

**Why this priority**: 답변 전체를 기다리지 않는 수신 계약을 후속 AI 연동보다 먼저 확정해야 한다.

**Independent Test**: 이벤트 소스의 완료를 보류한 상태에서 첫 Delta가 수신되는지 확인한 뒤 나머지 Delta와 완료를 검증한다.

**Acceptance Scenarios**:

1. **Given** 정상 이벤트 소스, **When** 요청 수락 및 스트림 시작, **Then** `text/event-stream` 응답의 첫 계약 이벤트는 `started`다.
2. **Given** 순차적으로 생성되는 여러 텍스트 조각, **When** 소스가 아직 완료되지 않은 상태, **Then** 생성된 Delta를 먼저 받을 수 있고 순서대로 결합할 수 있다.
3. **Given** 정상 완료하는 소스, **When** 마지막 Delta 이후, **Then** `completed`를 한 번 전송하고 연결을 종료한다. Delta가 0개인 정상 완료도 허용한다.

### User Story 3 - 신뢰할 수 없는 대화 맥락 차단 (Priority: P1)

서버는 방문자가 제출한 이전 대화의 역할·자료형·크기를 검증하며, 과거 `assistant` 메시지도 서버가 보증한 지시문으로 취급하지 않는다.

**Why this priority**: 위조한 대화 이력이 서버 권한이나 정책 변경의 근거가 되어서는 안 된다.

**Independent Test**: 역할 조작과 설정된 입력 한도 경계값을 제출하여 이벤트 소스 실행 전에 거부되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** `system`, `developer`, `tool` 또는 알 수 없는 역할, **When** 요청 검증, **Then** 스트림 시작 전에 거부한다.
2. **Given** 형식상 유효한 `assistant` 이력, **When** 처리 경계로 전달, **Then** 사용자 제공 맥락이라는 신뢰 수준을 유지한다.
3. **Given** 질문·이력·본문 중 하나가 설정된 한도를 초과, **When** 요청 제출, **Then** 스트림과 생성 작업을 시작하지 않는다.
4. **Given** 서버 설정이나 모델 지시를 바꾸려는 입력, **When** 질문이나 이력으로 제출, **Then** 텍스트 입력만으로 권한·시스템 정책이 변경되지 않는다.

### User Story 4 - 실패·타임아웃·연결 종료 구별 (Priority: P1)

클라이언트는 정상 완료와 실패를 구별하고, 서버는 더 이상 전달할 수 없는 응답을 위해 작업과 자원을 무기한 유지하지 않는다.

**Why this priority**: 부분 응답을 성공으로 오인하거나 끊긴 연결이 실행 자원을 점유하는 문제를 막아야 한다.

**Independent Test**: 시작 전 실패, 부분 Delta 이후 실패, 타임아웃, 쓰기 실패, 연결 종료 및 종료 콜백 경합을 각각 유발한다.

**Acceptance Scenarios**:

1. **Given** 응답 커밋 전 발생한 실패, **When** 서버가 감지, **Then** 일반 HTTP 오류로 응답하며 SSE 이벤트는 발생하지 않는다.
2. **Given** 일부 Delta가 전송된 스트림, **When** 처리 가능한 내부 오류 발생, **Then** 가능하면 `error`를 한 번 전송하고 종료하며 `completed`를 전송하지 않는다.
3. **Given** 연결 종료 또는 응답 쓰기 실패, **When** 서버가 감지, **Then** 남은 작업에 취소를 요청하고 자원을 정리한다. 전달 불가능한 terminal 이벤트는 보장하지 않는다.
4. **Given** 설정된 타임아웃 도달, **When** 종료 처리, **Then** 성공으로 기록하지 않고 작업 취소·자원 정리를 수행하며 쓰기 가능하면 `error`를 전달한다.
5. **Given** 완료·오류·취소 콜백 경합, **When** 중복 종료 시도, **Then** 종료 결과가 뒤집히거나 terminal 이벤트가 중복되지 않으며 후속 데이터를 전송하지 않는다.

### User Story 5 - 기존 기능 보존 및 로컬 검증 (Priority: P1)

관리자는 기존 CMS·인증 기능을 계속 사용하고, 개발자는 배포 서버나 실제 AI 없이 새 통신 계약을 검증한다.

**Why this priority**: 아직 없는 배포 환경을 전제로 진행하거나 기존 관리자 보안을 약화해서는 안 된다.

**Independent Test**: 기존 인증·CMS 회귀 테스트, 로컬 통신 검증, 설정 변경 및 요청 제한 검증을 수행한다.

**Acceptance Scenarios**:

1. **Given** 기존 관리자, **When** 로그인·인증 상태 조회·보호 API·로그아웃 사용, **Then** 기존 Session·인가·CSRF 정책이 유지된다.
2. **Given** OCI 서버·OpenAI Key·실제 AI 네트워크 호출이 없는 로컬 환경, **When** 계약 테스트 실행, **Then** 정상·오류·타임아웃·취소 경로를 재현한다.
3. **Given** 설정된 요청 또는 동시 스트림 한도 도달, **When** 추가 요청, **Then** 새 작업을 무제한 생성하지 않고 시작 전 429로 거부한다. 종료 후 점유 자원이 반환된다.
4. **Given** 실제 AI 처리기가 없는 운영 환경, **When** 유효한 요청, **Then** 시작 전 503 오류를 반환하며 테스트 답변을 실제 AI 답변으로 제공하지 않는다.
5. **Given** 환경별 Origin·한도·타임아웃 설정, **When** 설정 변경 후 실행, **Then** 동일한 요청·이벤트 계약을 유지하며 변경된 정책을 적용한다.

## Requirements *(mandatory)*

### Goal / Problem

이번 Phase의 목표는 비회원 질문의 입력 검증부터 점진적인 응답 전달, 종료와 자원 정리까지를 독립적으로 확인할 수 있는 백엔드 통신 기반 확립이다. HTTP 입력, AI 호출, CMS 검색, 추천 검증을 한 번에 결합해 오류 원인과 검증 책임이 섞이는 문제를 피한다.

### Scope / Out of Scope

포함 범위는 공개 POST 계약, 대화 맥락 검증, stateless 처리, SSE 이벤트·생명주기, 취소 가능한 실행 경계, 기본 요청·동시 실행 제한, 개인정보 로그 보호, 기존 보안 호환, 환경별 설정, 외부 AI 없는 자동화 검증이다.

제외 범위는 방문자 가입/로그인, CRM, 자체 상담원 채팅, WebSocket/STOMP, 영속 방문자 식별·이메일 검증·Magic Link·장기 상담 복원, 대화 DB 저장, 프런트엔드 코드, 실제 OpenAI 호출, CMS 검색·추천, 이미지 분석, 실제 배포 및 운영 고도화다. 기존 기능의 불필요한 수정과 잔존 테이블의 삭제도 포함하지 않는다.

### Functional Requirements

다음 FR-001~FR-024는 원본 요구사항의 식별자를 유지한다.

- **FR-001**: AI Chat 요청은 HTTP POST를 사용해야 한다. 운영 전송은 HTTPS를 사용한다.
- **FR-002**: 요청 본문은 JSON이어야 한다.
- **FR-003**: 성공적인 스트리밍 응답은 HTTP 200 및 `text/event-stream`이어야 한다.
- **FR-004**: 일반 사용자 계정 또는 Admin 로그인 없이 사용할 수 있어야 한다.
- **FR-005**: 현재 질문과 필요한 최근 대화를 하나의 요청에서 전달할 수 있어야 한다.
- **FR-006**: Conversation ID, ClientIdentity ID, persistent client token 등 장기 식별자를 요구하지 않아야 한다.
- **FR-007**: 공개 경로를 `POST /api/public/ai-chat/stream`으로 확정한다. 기존 `/api/public/**`·`/api/admin/**` 경계를 유지한다.
- **FR-008**: 현재 질문은 필수 문자열이며 비어 있거나 공백만으로 구성되면 거부해야 한다.
- **FR-009**: 전체 본문 바이트 수, 질문 길이, 이전 메시지 개수, 개별 이전 메시지 길이 및 전체 맥락 크기에 유한한 한도를 실제 적용해야 한다. 기본값·측정 단위·경계값은 Plan에서 확정하고 설정으로 변경 가능해야 한다. 전체 맥락 산정에는 현재 질문과 모든 이전 메시지 내용이 포함된다.
- **FR-010**: 외부 이력의 역할은 정확히 `user`, `assistant`만 허용해야 한다.
- **FR-011**: 클라이언트 제공 `assistant` 이력도 검증된 서버 메시지가 아닌 신뢰할 수 없는 입력으로 취급해야 한다.
- **FR-012**: 요청 데이터로 시스템 지시문, 서버 설정, 권한 또는 모델 정책을 변경할 수 없어야 한다.
- **FR-013**: 형식·크기·보안·수락 한도 검증에 실패하면 SSE와 이벤트 소스 실행을 시작하지 않아야 한다.
- **FR-014**: 전체 답변 완료 전 Delta를 순차 전달할 수 있어야 한다.
- **FR-015**: 시작·진행·정상 완료·오류·종료 상태를 구별해야 한다. 타임아웃·연결 종료·취소를 정상 완료와 구분해야 한다.
- **FR-016**: 중복 종료와 정리 호출, 종료 콜백 경합에도 terminal 이벤트 중복·종료 결과 변경·자원 손상이 없어야 한다.
- **FR-017**: 완료·실패·취소·타임아웃·쓰기 실패 후 실행 작업, 연결 관련 자원 및 동시 실행 점유를 정리해야 한다.
- **FR-018**: 스트리밍 내부 오류 후 연결과 작업이 무기한 유지되지 않아야 한다.
- **FR-019**: 연결 종료와 쓰기 실패를 감지하여 종료 처리로 연결할 수 있어야 한다. 물리적 단절의 즉시 감지를 보장하지 않는다.
- **FR-020**: 연결 종료 감지 시 해당 실행 작업에 취소를 요청할 수 있어야 한다. 응답 시작 전 감지에도 적용한다.
- **FR-021**: 취소 요청의 즉시 완료를 보장하지 않아야 하며, 취소 이후 결과로 새 데이터를 보내지 않아야 한다.
- **FR-022**: 유한한 SSE 타임아웃을 환경별로 설정하고 실제 적용해야 한다.
- **FR-023**: SSE 응답 커밋 이후 실패는 HTTP 상태 변경이나 일반 JSON 본문 교체로 처리하지 않아야 한다.
- **FR-024**: `completed` 없는 종료, 부분 답변 이후 오류, 타임아웃·취소·쓰기 실패를 성공으로 처리하지 않아야 한다.
- **FR-025**: 이벤트 이름·데이터·순서·terminal 규칙은 아래 SSE 계약을 준수해야 한다.
- **FR-026**: 각 요청을 독립 처리하고 방문자별 대화 상태를 장기 보관하거나 방문자 대화 원문을 DB에 저장하지 않아야 한다.
- **FR-027**: Conversation, Message, ClientIdentity, ClientCredential, Visitor Session, Chat History 엔티티·테이블·저장 흐름을 새로 도입하거나 재활성화하지 않아야 한다. 기존 baseline 잔존 테이블을 새 채팅의 저장소로 사용하지 않는다.
- **FR-028**: 시작 전 오류는 기존 `ApiResponse<ErrorResponse>`의 상태·코드·메시지·선택적 필드 오류 구조를 유지해야 한다. 거부된 입력 원문을 응답에 포함하지 않는다.
- **FR-029**: 실제 AI 처리기가 없는 운영 요청은 시작 전 503으로 실패해야 한다. 제어 가능한 이벤트 소스는 테스트/명시적인 로컬 검증에서만 사용하고 실제 AI 생성 결과로 표시하지 않는다.
- **FR-030**: 후속 공급자 고유 이벤트를 브라우저 계약과 분리하고, 향후 AI·검색 연동이 기존 POST/SSE 계약의 재작성을 요구하지 않는 경계를 유지해야 한다.
- **FR-031**: 새로운 이벤트는 기존 네 이벤트의 의미·필드를 깨지 않는 추가 방식으로 확장해야 한다. 미지원 이벤트 이름은 소비자가 건너뛸 수 있도록 계약에 명시한다. 추천 이벤트는 이번 Phase에서 생성하지 않는다.

### Request Contract

| 항목 | 계약 |
| --- | --- |
| Method / Path | `POST /api/public/ai-chat/stream` |
| Request Content-Type | `application/json` |
| Response Accept | `text/event-stream`과 호환되는 미디어 범위 허용. 생략 또는 `*/*` 허용, 명시적으로 호환되지 않으면 406 |
| `message` | 필수, 비공백 문자열, 현재 질문 |
| `history` | 선택적 배열, 생략 시 빈 배열과 동일, `[]` 허용, 명시적 null 거부 |
| `history[].role` | 필수 문자열, `user` 또는 `assistant` |
| `history[].content` | 필수 비공백 문자열, 텍스트 길이 한도 적용 |
| 순서 | `history`의 전달 순서를 유지하고 현재 `message`를 뒤에 오는 질문으로 구분 |

```json
{
  "message": "패키지 디자인 작업물을 보여줘.",
  "history": [
    {"role": "user", "content": "두이드에서 어떤 디자인을 제작해?"},
    {"role": "assistant", "content": "브랜드와 작업물에 관한 안내를 제공할 수 있어요."}
  ]
}
```

이 예시는 입력 데이터 형식이며 Phase 07이 검색이나 답변 생성을 제공한다는 의미가 아니다. 이력은 클라이언트가 선택해 보낸 맥락이며 원본성·완전성·역할 교대·실제 과거 발화 여부를 보증하지 않는다. 본문에 모델·서버 권한·시스템 지시문을 변경하는 제어 필드를 제공하지 않는다.

### SSE Event Contract

성공 응답은 UTF-8 SSE 스트림이다. 각 이벤트는 명시적 `event` 이름과 JSON 객체인 `data`, 이벤트를 구분하는 빈 줄로 구성한다. 성공 스트림 전체나 각 이벤트 데이터를 기존 `ApiResponse` JSON으로 감싸지 않는다. 이는 이번 사용자 요청에 따른 SSE 전용 계약이며 일반 JSON 오류/기존 API 래퍼 규칙은 유지한다.

| Event | 필수 data | 의미 |
| --- | --- | --- |
| `started` | `{"requestId":"example-request-id"}` | 수락 및 스트림 시작. 요청별 임시 추적 문자열, 방문자 식별/상담 복원 용도 금지 |
| `message_delta` | `{"text":"패키지 디자인"}` | 순서대로 결합할 텍스트 일부 |
| `completed` | `{"status":"success"}` | 유일한 정상 완료 표시 |
| `error` | `{"code":"STREAM_FAILED","message":"응답을 처리하지 못했습니다.","retryable":false}` | 처리 가능한 스트림 실패. 코드·안전한 메시지·boolean 재시도 안내 필수 |

정상적인 wire 형식 예시이며, 각 `data` 다음의 빈 줄도 계약의 일부다.

```text
event: started
data: {"requestId":"example-request-id"}

event: message_delta
data: {"text":"패키지 디자인"}

event: message_delta
data: {"text":" 작업물을 소개해 드릴게요."}

event: completed
data: {"status":"success"}

```

- **SSE-001**: 정상 흐름은 `started` 1개 → `message_delta` 0..N개 → `completed` 1개 → 연결 종료다.
- **SSE-002**: 쓰기 가능한 실패 흐름은 `started` 1개 → `message_delta` 0..N개 → `error` 1개 → 연결 종료다. `completed`와 `error`는 상호 배타적이다.
- **SSE-003**: terminal 결정 이후 새 Delta·시작·다른 terminal을 전송하지 않는다. 물리적 단절/쓰기 실패로 terminal 전달이 불가능하면 전달을 보장하지 않는다.
- **SSE-004**: 응답 커밋 후 `started` 전달 자체에 실패한 경우도 일반 JSON으로 전환하지 않는다. 취소·정리하고 비정상 종료로 남긴다.
- **SSE-005**: 정상 완료는 `completed` 수신으로만 판별한다. `error` 수신은 명시적 실패이며, 둘 다 없이 끝난 경우도 비정상 종료다.
- **SSE-006**: 네트워크 청크와 이벤트는 1:1 관계가 아니다. 청크 병합·분할에도 UTF-8, JSON 특수문자·개행, 이벤트 구분이 보존되어야 한다.
- **SSE-007**: 오류 데이터에 내부 예외·API Key·설정·프롬프트·요청/응답 원문을 넣지 않는다. `retryable`은 재시도 안내일 뿐 자동 재시도·중복 실행 방지를 보장하지 않는다.
- **SSE-008**: 이벤트 이름과 위 필수 필드는 고정한다. 오류 코드 목록과 타임아웃 코드·재시도 분류의 상세 매핑은 Plan에서 확정하되 일반 처리 실패 `STREAM_FAILED`를 유지한다.
- **SSE-009**: 자동 재접속, 이벤트 재생, `Last-Event-ID` 기반 복원은 제공하지 않는다. `requestId`를 영속 식별자 또는 재실행 방지 키로 사용하지 않는다.

### Error Handling / Streaming Lifecycle

검증·요청 제한·처리기 가용성은 응답 커밋 전에 판정한다. HTTP 응답 커밋 시점이 일반 오류와 SSE 오류의 경계다. `started` 생성 여부만으로 HTTP 상태 변경 가능성을 판단하지 않는다.

| 상황 | 커밋 전 응답 | 커밋 후 동작 |
| --- | --- | --- |
| 입력 형식·역할·텍스트/맥락 한도 위반 | 400 + 공통 JSON 오류 | 검증을 이미 완료해야 하므로 정상 경로에서 발생하지 않음 |
| 본문 바이트 한도 초과 | 413 + 공통 JSON 오류 | 시작 전 제한 |
| 지원하지 않는 Content-Type / Accept | 415 / 406 + 공통 JSON 오류 | 시작 전 제한 |
| 요청·동시 스트림 한도 초과 | 429 + 공통 JSON 오류 | 시작 전 제한 |
| 처리기 미준비·스트리밍 기능 사용 불가 | 503 + 공통 JSON 오류 | 가능하면 `error`, 이후 종료·정리 |
| 예상하지 못한 내부 오류 | 500 + 안전한 공통 JSON 오류 | 가능하면 `error`, 이후 종료·정리 |
| 타임아웃 | 시작 전 감지 시 안전한 HTTP 오류 | 가능하면 `error`, 취소·정리, 성공 완료 금지 |
| 연결 종료·쓰기 실패 | 전달 불가능하면 응답 보장 없음 | 추가 쓰기 중단·취소 요청·정리 |

종료 정리에는 실행 작업 취소 요청, 콜백/연결 관련 자원 반환 및 동시 스트림 점유 반환이 포함된다. 실패한 쓰기를 무한 재시도하지 않으며, 오류 이벤트의 전송 실패가 정리를 막지 않아야 한다. 취소를 처리하는 실행 경계와 종료의 단일 결과를 유지하되 구체적인 클래스·동시성 수단은 이 명세에서 정하지 않는다.

### Security Requirements

- **SEC-001**: AI Chat에 Admin 인증을 요구하지 않는다.
- **SEC-002**: 공개 접근 허용 범위를 이유로 Admin API 접근 권한이나 다른 미등록 경로의 접근 범위를 확대하지 않는다.
- **SEC-003**: 기존 Admin Session, 로그인·로그아웃·인증 상태 조회, CSRF와 권한 검증을 보존한다. 채팅 기능을 위해 전역 Session 정책을 stateless로 바꾸지 않는다.
- **SEC-004**: 채팅 POST의 CSRF 방식은 비회원 stateless 특성과 함께 전송될 수 있는 Admin Session을 고려해 Plan에서 결정한다. 전체 API CSRF 비활성화 또는 `/api/public/**` 전체 면제는 허용하지 않는다. 채팅 수락이 Admin 세션 권한을 사용하거나 변경해서는 안 된다.
- **SEC-005**: 입력 역할·자료형·크기를 스트림 실행 전에 검증한다.
- **SEC-006**: 사용자 제공 이력과 서버 시스템 지시문의 신뢰 경계를 분리한다.
- **SEC-007**: 입력이나 쿠키 조작으로 서버 권한·신뢰 수준·요청 한도 우회 권한을 얻을 수 없어야 한다.
- **SEC-008**: 후속 CMS 검색 결과나 외부 AI 응답도 자동으로 신뢰할 수 있는 지시나 데이터가 되지 않도록 경계를 유지한다. 해당 기능은 이번에 구현하지 않는다.
- **SEC-009**: 공개 요청에 유한하고 설정 가능한 최소 요청 빈도 제한을 실제 적용한다. 단순히 추후 연결 가능한 빈 경계만 제공하는 것은 완료로 인정하지 않는다.
- **SEC-010**: 동시에 실행 가능한 스트림 수에 유한하고 설정 가능한 한도를 실제 적용한다. 실행/대기 자원 역시 무제한 증가하지 않아야 한다.
- **SEC-011**: 제한 초과는 새 작업 생성 전에 429로 거부한다. 시간 창·범위·요청자 구분·한도·점유 반환 검증을 Plan에서 확정한다. 프록시 전달 헤더를 요청자 구분에 사용한다면 클라이언트가 임의로 신뢰 경계를 우회하지 못해야 한다.
- **SEC-012**: 제한 정책을 위해 Redis 등 새로운 상시 인프라를 요구하지 않는다. 단일 프로세스 한도인지 분산 한도인지 Plan에서 명시하고 제공하지 않는 보장을 주장하지 않는다. Phase 08의 과금 호출 전에도 남용 방지 정책을 적용한다.
- **SEC-013**: 질문·이력·생성 답변 원문을 일반 로그·접근 로그·예외 메시지에 기록하지 않는다. 진단에는 임시 요청 ID, 안전한 오류 코드, 소요 시간, 종료 사유 등 원문 없는 정보를 사용한다.
- **SEC-014**: 오류 응답·SSE 오류·로그에 Stack Trace의 민감한 메시지, 키, 서버 환경변수, 프롬프트, 입력/출력 원문이 노출되지 않아야 한다.
- **SEC-015**: 임시 요청 식별자를 장기 방문자 추적·브라우저 저장 상태 연동·상담 복원에 사용하지 않는다. 채팅 처리를 위해 방문자 세션이나 영속 쿠키를 만들지 않는다.
- **SEC-016**: 개인정보 관련 입력 검증을 완전한 익명화나 법적 적합성 보장으로 설명하지 않는다. 법적 적합성 최종 점검은 Phase 12의 별도 범위다.

### Backend Feature Boundary / Stateless Policy

AI Chat의 책임은 HTTP 전달, 입력 검증, application 처리 경계, 이벤트 소스 연결, SSE 매핑·생명주기 및 요청 보호로 제한한다. 기존 feature-first 구조와 의존 방향을 유지하며 controller에서 repository나 외부 client를 직접 호출하지 않는다. 핵심 처리 흐름을 후속 이벤트 리스너로 위임하지 않는다.

현재 `ai` 영역은 백엔드를 통한 LLM 접근 경계라는 지침만 있으며 구현은 없다. 해당 책임을 유지하는 방향으로 기반을 추가하되 구체적인 클래스·Interface·Adapter·하위 패키지는 Plan에서 결정한다. 방문자 영속 상담을 위해 `chat`/`client` 모델을 재도입하지 않는다. Category·Media·Work·Admin 계정 모델은 불필요하게 변경하지 않는다.

요청 처리 중의 일시적인 메모리 사용만 허용한다. Zustand·sessionStorage의 대화 보관은 프런트엔드 책임이며 서버 DB 동기화는 제공하지 않는다. 후속 CMS 협력은 명시적인 application contract 및 기존 query-side 예외 규칙을 따르고 다른 feature의 구현체에 직접 의존하지 않는다.

### Local Development / Deployment Readiness

- **LOCAL-001**: OCI 없이 로컬에서 계약·생명주기·보안 테스트를 실행할 수 있어야 한다. 기존 DB 회귀 검증에 필요한 로컬 컨테이너 런타임은 별도 전제다.
- **LOCAL-002**: OpenAI Key·실제 외부 AI 호출 없이 제어 가능한 소스로 정상·실패·타임아웃·취소를 검증해야 한다. 테스트 소스가 운영 응답으로 노출되지 않아야 한다.
- **LOCAL-003**: 허용 Origin, 본문·질문·이력·맥락 한도, SSE 타임아웃, 동시 스트림 한도, 요청 제한 정책을 기존 환경별 설정 체계로 분리한다. 후속 공급자 설정도 같은 원칙을 따르며 이번에 키/SDK 설정을 필수화하지 않는다.
- **LOCAL-004**: 로컬 주소·포트·Vercel URL·OCI IP·운영 도메인·개발 Secret을 핵심 코드에 고정하지 않는다. 환경값과 민감정보를 분리한다.
- **LOCAL-005**: 추후 HTTPS, CORS/preflight, 장시간 연결, 스트리밍 버퍼링, 프록시 타임아웃, 연결 종료, 동시 실행 제한 및 자원 정리를 설정·검증할 수 있어야 한다. 미래 배포를 위해 핵심 처리 코드나 통신 계약을 다시 작성하지 않아야 한다.

## Assumptions

### 확인한 기존 상태와 충돌 해석

- Git 루트는 저장소 상위 디렉터리이며 SpecKit 설정·템플릿·기존 Phase 01~06 산출물은 `apps/api` 아래에 있다. 명세 생성 당시 브랜치는 `main`이었다. 명세 단계의 사용자 요청으로 자동 브랜치 생성 스크립트를 실행하지 않고 `apps/api/specs/007-ai-chat-foundation`에 직접 작성한다.
- `build.gradle`에서 Spring Boot 4.0.6, Java 25, Spring MVC, Spring Security, JPA, OpenFeign QueryDSL 7.4.0 및 기존 테스트 의존성을 확인했다. Redis/WebSocket 의존성의 존재가 이번 기능에서 해당 인프라/프로토콜을 사용한다는 뜻은 아니다. 버전 변경·추가 라이브러리는 이번 범위가 아니다.
- `src/main/java/kr/douid/brand/ai`에는 `CLAUDE.md`만 존재한다. 기존 AI 구현·스트림 처리기가 있다고 가정하지 않는다.
- `SecurityConfig`는 공개 경로 허용, Admin 역할 보호, 기본 거부, `IF_REQUIRED` Session 및 쿠키 기반 CSRF 정책을 사용한다. 현재 공개 경로 허용만으로 POST의 CSRF 검증이 면제되는 것은 아니다. 채팅의 세부 CSRF 설정은 Plan에서 결정한다.
- `ApiResponse`, `ErrorResponse`, `GlobalExceptionHandler`는 일반 JSON 오류의 기반이다. 현재 handler가 새 채팅의 모든 4xx/스트림 오류를 이미 정확히 처리한다고 가정하지 않는다. 일반 JSON 래퍼 규칙과 SSE의 충돌은 명시적인 사용자 SSE 계약을 우선하여 해석한다.
- `V1__baseline_schema.sql`에는 `client_identity`, `client_credential`, 이메일 검증/복구, `conversation`, `message` 등의 이전 테이블 정의가 남아 있다. 코드 롤백이 물리적 스키마 제거 완료를 뜻하지 않는다. 새 생성/사용 금지와 기존 잔존 테이블 부재를 구분하며 baseline 수정·테이블 삭제를 이번 요구사항으로 삼지 않는다. 실제 배포 DB 존재/상태는 확인하지 않았다.
- `PostgresIntegrationTest`는 PostgreSQL 17 계열 컨테이너, Flyway 및 스키마 검증을 사용한다. `SecurityConfigTest`, `CsrfCookieFlowTest`에서 기존 Session·CSRF·CORS 및 폐기된 Client API 차단 검증을 확인했다. 테스트 파일 존재 확인은 현재 실행 성공의 증거가 아니다.
- `.specify/memory/constitution.md`는 미작성 템플릿이다. 완성된 헌법으로 간주하지 않으며 기존 CLAUDE 지침과 현재 요청을 기준으로 작성한다. 루트 지침에 남은 자체 실시간 상담/장기 Client 기능 설명은 이번 명시적 제외 범위를 뒤집는 요구사항으로 해석하지 않는다.

### 계약 기본 해석 및 Plan에 남기는 결정

- `history` 생략은 빈 배열로, 명시적 null은 잘못된 자료형으로 해석한다. 역할은 소문자 정확 일치이며 유효한 이력에 별도 교대 순서를 강제하지 않는다.
- 운영 AI 처리기 미준비는 503, 요청/동시 실행 한도 초과는 429로 통일한다. 공통 JSON 오류 코드의 추가 목록과 타임아웃의 시작 전 상태 매핑은 Plan에서 확정한다.
- 구체적인 제한 기본값·단위·시간 창·적용 범위·요청자 식별 방식, CSRF 세부 방식, 실행·취소·동시성 수단, 스트림 지원 클래스, 공급자 경계의 구체 타입, 테스트 도구/파일, 설정 키는 Plan의 결정 사항이다. 양의 유한한 한도 적용과 계약상 동작은 선택 사항이 아니다.
- 수치 한도가 미정인 검증은 Plan에서 정한 설정값을 기준으로 바로 아래·정확한 한도·초과를 검사한다. 이번 문서에 임의의 운영 처리량·지연 SLA를 추가하지 않는다.
- 실제 SSE를 수신하는 소비자는 JSON 오류 응답과 스트림을 구분하고 이벤트 단위로 조립해야 한다. 프런트엔드 구현과 배포 통합 검증은 완료로 가정하지 않는다.
